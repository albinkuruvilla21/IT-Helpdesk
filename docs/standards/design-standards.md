# Design standards

How an accepted design or prototype becomes a canvas app. Two documents divide the work:

| Document | Scope | Changes |
|---|---|---|
| **This one** | The **mechanics**: token architecture, states, accessibility, how a design maps onto screens and components | Rarely. A change here is a template change, with a CHANGELOG entry |
| **`specs/design-spec.md`** (per project, from [the template](../templates/design-spec.template.md)) | The **values**: this client's colours, type, spacing, every screen's and component's anatomy and states | Per project, generated by `/design-spec` (stage G3) |

## 1. The rule that governs everything else

**A client's app follows the client's brand, not Acies'.** What carries over from project to project is
the mechanism (token names, the accessibility floor), never the values. Shipping a client app in Acies
colours is a delivery failure, not a styling nit.

## 2. Source precedence

When the inputs disagree, the higher one wins, and the design spec records the conflict:

1. **Approved acceptance criteria**: what the app must do, and what the PO excluded.
2. **The accepted design or prototype** (PNG, PDF or HTML; a clickable prototype's screens): what it
   must look like **and how it must behave**: layout, controls, wording, user flows, validations,
   messages, states. It is the primary reference for the UI; where a criterion doesn't spell a detail
   out, the prototype settles it ([prototype-fidelity.md](prototype-fidelity.md)).
3. **The client's brand guidelines**: the palette, type and logo rules the design should have followed.
4. **This document**: how it is built, and the accessibility floor, which **overrides all three**. A
   design colour that fails contrast gets a compliant variant, recorded in design-spec §8, and the
   design lead tells the client.

## 3. Tokens

Every visual value is a **named formula in `App.Formulas`** (`canvas/<App>/Src/App.pa.yaml`).
Screens and components use the **names**; `/design-spec` sets the **values**. Named formulas are
evaluated when used, cost nothing at start-up, and can't be overwritten at run time.

| Group | Names | Rule |
|---|---|---|
| Brand | `ColorPrimary`, `ColorPrimaryHover`, `ColorPrimaryPressed`, `ColorOnPrimary`, `ColorPrimaryTint`, `ColorSecondary` | `ColorOnPrimary` on `ColorPrimary` ≥ 4.5:1 |
| Neutral | `ColorText`, `ColorTextMuted`, `ColorBorder`, `ColorDivider` | Text ≥ 4.5:1 on surface **and** background; `ColorBorder` ≥ 3:1; `ColorDivider` never carries meaning |
| Surface | `ColorBackground`, `ColorSurface`, `ColorSunken` | Cards (`ColorSurface`) sit on `ColorBackground`. Never white on white |
| Semantic | `ColorSuccess`, `ColorWarning`, `ColorError`, `ColorInfo` + `…Fill` | Kept apart from the brand hue, so a red brand never reads as an error |
| Typography | `FontBody` (a `Font.` value) | Sizes are plain numbers in Studio points, **measured from the prototype**: px × (app content width / prototype content width) × 0.75 (`canvas_ui.Design.pt`) |
| Space | `SpaceXs`, `SpaceS`, `Space`, `SpaceL`, `SpaceXl` on a 4/8 grid | Add steps at the ends, never between |
| Shape | `Radius`, `BorderThickness`, `FocusThickness` | One focus style, visible on every surface |
| Layout | `HeaderHeight`, `BreakpointNarrow` | |
| Prototype surfaces | `ColorGlass`, `ColorGlassStroke`, `ColorField`, `ColorSegment`, `ColorSegmentOn`, `ColorBackdrop1`... | Named after the prototype's custom properties by `tools/prototype_design.py`; translucent ones keep their alpha |
| Scheme | `IsDark`, and each colour token `If(IsDark, <dark>, <light>)` | When the prototype defines a dark scheme. `IsDark = Coalesce(First(colScheme).Value, "Light") = "Dark"`; `colScheme` is loaded from configuration (the device setting cannot be read) |
| SVG colours | `Hex<Name>` text named formulas (`HexPrimary`) | For colours inside SVG images (rings, backdrops, tiles); same values as the RGBA tokens |

The starter's `App.pa.yaml` has a subset; `/design-spec` adds the rest. When a client needs a token
that doesn't exist (a second accent), **add it with a comment saying which design element needs it**.
Never put the literal on a screen: `pp.py` doesn't stop it, `/verify` check 3 does.

**Fonts.** Canvas apps use the fonts Power Apps offers (`Font.'Segoe UI'`, `Font.'Open Sans'`, …) and
whatever the user's device has. A brand font outside that list is not available: choose the closest
offered font, and record it in design-spec §3 and §9.

## 4. Mapping a design onto a canvas app

A design shows pages; a canvas app has **screens**, **components** and **flows**. `/build-plan`
records the mapping in `specs/build-plan.md`, and the AC workbook's *Power Apps Component* column
names the piece each criterion lives in.

| Design element | Becomes | AC *Power Apps Component* |
|---|---|---|
| A page or full view | One screen, `scr<Name>` | `<App>: scr<Name>` |
| A header, navigation or footer on every screen | The same **controls placed on each screen** (header band, title, subtitle, user, navigation strip, tabs, underline), exactly as `ui-patterns.md` §3 and `canvas_ui.chrome()`; not a container. A canvas component (`cmp<Name>`) made in Studio is a spike (CLAUDE.md §6) | `<App>: conHeader (every screen)` |
| A dialog, panel or confirmation | A component or a container shown by a variable, on the screen that opens it | `<App>: scr<Name>` |
| A list of records | A gallery bound to a list (delegable) | `<App>: scr<Name>` |
| A form to create or edit a record | An edit form (or inputs + `Patch`) on its screen | `<App>: scr<Name>` |
| Something that happens without the user (email, reminder, schedule) | A cloud flow in the solution | `Flow: <display name>` |
| Something the user starts that needs a connector the app shouldn't hold | A flow called from the app (Power Apps trigger) | `Flow: <display name>` |
| App-wide behaviour (start screen, theme, error handling) | `App` properties | `<App>: App` |

`<App>` is the app's source folder name (`canvas/<App>/`).

## 5. States every data-backed screen has

| State | Pattern | Never |
|---|---|---|
| Loading | A loading indicator where the data will be (`LoadingSpinner` on data screens, or a placeholder container) | A frozen screen with no feedback |
| Empty | A label saying what's missing and why, and the next step (a button) if there is one | A blank gallery |
| Error | `IfError(…)`/`Errors(…)` caught; a `Notify` or label in the user's words, and a way to retry | A raw error text, or silence |
| Ready | The design | |
| No permission | Said plainly when SharePoint refuses (`Errors()` shows a 403) | Hiding the screen as "the" access control |

The design spec states what each of these looks like for each screen. Designs usually show only "ready".

## 6. Layout and responsiveness

- The app's base size is set at G3 (tablet 1366 × 768 by default; phone only when the AC says so).
  *Scale to fit* is **off** for responsive apps; on for fixed-size apps.
- Layout follows **[ui-patterns.md](ui-patterns.md)**: header and navigation placed on the screen, ONE scrolling auto-layout body, sections with
  explicit heights, tables as a gallery in a fixed-height wrapper. Sizes are plain numbers measured from the prototype (prototype-fidelity §8), the reference numbers there only where the prototype gives none; do not compute them from tokens.
- Check each screen at the base width, at `BreakpointNarrow` and at the narrowest supported width. No
  horizontal scroll at 320 px equivalent (WCAG 1.4.10 reflow) for apps used on phones.
- One navigation pattern for the whole app, from the header/navigation component.

## 7. Accessibility in design

[dev-standards.md §7](dev-standards.md#7-accessibility--wcag-21-aa-always) is the checklist. At design
time specifically:

- Contrast is checked for **every** text/background pair in the design spec's token table, in every
  state (hover, pressed, disabled, focus). Record the ratio.
- Focus is designed: `FocusedBorderColor` and `FocusedBorderThickness` from tokens, visible on light
  and dark surfaces.
- Icon-only buttons have an accessible name in the spec (`AccessibleLabel` on the icon).
- Nothing auto-advances (timers, carousels) unless the AC says so, and then it can be paused.

## 8. Fidelity

The prototype is translated, not redesigned ([prototype-fidelity.md](prototype-fidelity.md), CLAUDE.md §7).
Every element and behaviour it shows is a row in `specs/prototype-fidelity.md`.

| Match exactly | Adapt, and record in design-spec §9 |
|---|---|
| Colours in every scheme the prototype defines, as tokens | Fonts Power Apps doesn't offer |
| Type sizes and weights, radii, spacing, shadows, translucency, the page background, the chrome: measured (prototype-fidelity §8) | Backdrop blur; following the device's light/dark setting automatically |
| Screens, regions, content order, hierarchy, grouping, alignment and proportions | Interactions a canvas app can't do (hover-only menus, drag-and-drop between lists) |
| Every control, of the same kind wherever a native one exists | A control with no checked equivalent: the closest checked one, and a spike |
| Every label, heading, button text, placeholder and message, verbatim | Interactions that fail accessibility |
| User flows: each action's result, navigation, confirmation and message | Pixel sizes that don't fit the app's base size. Keep the proportion |
| Validations: the rule, when it fires, its message and where it shows | |
| Conditional display and enablement, sort orders, derived values and their formats | |
| Screen states the design shows | |

Only a platform limitation (prototype-fidelity §6) or a client decision justifies the right-hand column.
"Simpler" never does. A deviation nobody records turns into a bug report at UAT.
